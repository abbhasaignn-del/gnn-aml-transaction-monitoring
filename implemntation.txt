# Phase 3 — Build the Transaction Graph

The central concept of your project is the graph.

Represent:

```text
Account = Node
Transaction = Edge
```

Example:

```text
A101 ──₹50,000──> A205
 │                  │
 │                  ▼
 └──────────────> A310
                    │
                    ▼
                   A101
```

This allows the system to capture relationships between multiple accounts instead of analyzing transactions independently, which is one of the project's main objectives. 

### Node features

For each account:

```text
total_transactions
total_sent
total_received
average_transaction
number_of_counterparties
account_age
country
risk_history
```

### Edge features

For each transaction:

```text
amount
timestamp
transaction_type
channel
country
frequency
```


# Phase 5 — Develop the GNN

For your first version, use **GraphSAGE**.

Recommended stack:

```text
Python
PyTorch
PyTorch Geometric
```

Basic architecture:

```text
Input Node Features
       │
       ▼
GraphSAGE Layer 1
       │
       ▼
ReLU
       │
       ▼
GraphSAGE Layer 2
       │
       ▼
Fully Connected Layer
       │
       ▼
Risk Probability
```

Example output:

```text
Account A101
Risk Score = 0.12

Account A205
Risk Score = 0.87

Account A310
Risk Score = 0.94
```

Then define thresholds:

```text
0.00 – 0.30 → Low Risk
0.30 – 0.70 → Medium Risk
0.70 – 1.00 → High Risk
```

These thresholds should be configurable rather than hard-coded.

# Phase 6 — Model Training

Split the data carefully.

```text
Historical Transactions
          │
          ▼
      Training Data
          │
          ▼
     GNN Training
          │
          ▼
     Validation Data
          │
          ▼
       Evaluation
```

Important metrics:

* Precision
* Recall
* F1-score
* ROC-AUC
* PR-AUC
* False-positive rate
* False-negative rate

For AML, don't rely only on accuracy because suspicious transactions may represent a small portion of all transactions.

# Phase 7 — Real-Time Transaction Pipeline

Use **Apache Kafka** for streaming.

```text
Transaction Producer
        │
        ▼
     Kafka Topic
   "transactions"
        │
        ▼
Transaction Consumer
        │
        ▼
Preprocessing
        │
        ▼
Graph Update
        │
        ▼
GNN Inference
        │
        ▼
Risk Score
```

Example incoming event:

```json
{
  "transaction_id": "TX1001",
  "sender": "A101",
  "receiver": "A205",
  "amount": 95000,
  "timestamp": "2026-09-18T10:30:00"
}
```

The system should process this transaction and return something like:

```json
{
  "transaction_id": "TX1001",
  "risk_score": 0.91,
  "risk_level": "HIGH",
  "alert": true
}
```

# Phase 10 — Explainability

This is important because the document identifies difficulty explaining GNN decisions as a disadvantage. 

Don't show only:

```text
Risk = 0.92
```

Instead provide:

```text
Risk Score: 0.92

Contributing factors:
✓ High transaction frequency
✓ Large amount
✓ Multiple connected accounts
✓ Circular transaction relationship
✓ Previously suspicious connected account
```

You can investigate **GNNExplainer** or related graph explainability techniques for the advanced version.
